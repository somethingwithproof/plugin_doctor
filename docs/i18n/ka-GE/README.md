Cacti Doctor არის Cacti-ის პლაგინი, რომელიც ერთი გავლით ატარებს ინსტალაციის დიაგნოსტიკას და მცირე შეკეთებებს მხოლოდ მაშინ ასრულებს, როდესაც ამას ადმინისტრატორი მოითხოვს.

**სტატუსი: დამუშავების პროცესში, 1.0 ვერსიამდე.** უახლესი გამოშვებაა [0.6.1](https://github.com/somethingwithproof/plugin_doctor/releases/tag/v0.6.1). ეს პატჩი 0.6.0 ვერსიის როლებზე დაფუძნებულ წვდომას, მართულ დიაგნოსტიკას, შეზღუდულ RRD აქტუალობის შემოწმებებს, შეკეთების წინასწარ ხედვასა და აუდიტის ისტორიას, მიღებულ გაფრთხილების გამონაკლისებსა და თარგმანებს უმატებს ჰინდისა და არაბული ენის კატალოგებს და ნათარგმნ სახელმძღვანელოებს. დეტალებისთვის იხილეთ [CHANGELOG.md](../../../CHANGELOG.md).

## ეკრანის ანაბეჭდები

დიაგნოსტიკისა და დაგეგმვის პარამეტრები იზოლირებულ Cacti 1.2.31 სადემონსტრაციო ინსტალაციაში PHP 8.3.36-ზე, მათ შორის Cacti-ის PHP თავსებადობის, უსაფრთხოების ძირითადი მხარდაჭერისა და მონაცემთა ბაზის მდგომარეობის შემოწმებები. აქ ნაჩვენები გაფრთხილებები და შეცდომები აღწერს ამ სადემონსტრაციო გარემოს.

![Doctor-ის დიაგნოსტიკური ცხრილი წარმატებული, გაფრთხილებისა და შეცდომის შედეგებით](../../screenshots/diagnostics.png)

![Doctor-ის დაგეგმვის, შეტყობინებებისა და ზღვრების პარამეტრები](../../screenshots/settings.png)

Cacti-ის პრობლემები ჩვეულებრივ სიმპტომების სახით ვლინდება: ცარიელი გრაფიკები, გაჩერებული პოლერი ან პლაგინი, რომელიც არ ყენდება. მიზეზი ხშირად შეცვლილი წინაპირობაა — მაგალითად, CLI ბილდში გამოტოვებული PHP გაფართოება, ჟურნალის დირექტორია, რომელშიც პოლერს ჩაწერის უფლება არ აქვს, არასწორ ბინარულ ფაილზე მიმართული RRDtool-ის გზა ან დროის სარტყლის ცხრილების გარეშე დარჩენილი მონაცემთა ბაზა. Doctor პირდაპირ ამოწმებს ამ წინაპირობებს და თითოეულს აფიქსირებს როგორც წარმატებულს, გაფრთხილებას ან შეცდომას, აღმოჩენილის განმარტებით წინადადებასთან ერთად. იგივე ანგარიში ხელმისაწვდომია ვებ-გვერდზე, ბრძანების სტრიქონში და მონიტორინგისთვის JSON ფორმატში.

## მონაცემთა ბაზის მდგომარეობის რჩევები

Doctor-ის შიდა PHP ანალიზატორი Cacti-ის არსებული მონაცემთა ბაზის კავშირით კითხულობს MySQL-ის ან MariaDB-ის გლობალური მთვლელების ფიქსირებულ ნაკრებს. ის თითოეულ ანგარიშზე მხოლოდ ორ წაკითხვის მოთხოვნას ასრულებს, არ საჭიროებს დამატებით მონაცემებს ან გარე პროგრამას და არასდროს ცვლის მონაცემთა ბაზის კონფიგურაციას. ეს შემოწმებები ჩანს ვებ-ანგარიშში, CLI-ში, JSON-ში, მონიტორინგის გამომავალში, მხარდაჭერის პაკეტსა და დაგეგმილ სტატუსის თვალთვალში.

| შემოწმების ID | გამოკვლევის საფუძველი |
|---|---|
| `database.health_sample` | გაშვებიდან ან `FLUSH STATUS`-დან 24 საათზე ნაკლები დრო, ან მიუწვდომელი/არათანმიმდევრული მუშაობის დრო |
| `database.connection_capacity` | მიმდინარე ან დაფიქსირებული პიკური კავშირები მიმდინარე `max_connections`-ის სულ მცირე 80% |
| `database.buffer_pool_reads` | `Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests` სულ მცირე 1%, სულ მცირე 10,000 წაკითხვის მოთხოვნით |
| `database.temporary_tables` | `Created_tmp_disk_tables / Created_tmp_tables` სულ მცირე 25%, სულ მცირე 1,000 დროებითი ცხრილით |
| `database.thread_cache` | `Threads_created / Connections` სულ მცირე 5%, სულ მცირე 1,000 კავშირის მცდელობით და `thread_handling=one-thread-per-connection` რეჟიმით |
| `database.slow_queries` | `Slow_queries / Queries` სულ მცირე 1%, სულ მცირე 1,000 მოთხოვნით |
| `database.redo_log_waits` | ნულისგან განსხვავებული `Innodb_log_waits` |

ეს არის Doctor-ის გამოკვლევის ზღვრები და არა მწარმოებლის კონფიგურაციის მიზნობრივი მნიშვნელობები. კავშირების ტევადობის გარდა, კუმულაციური რჩევები მოითხოვს ზემოთ აღნიშნულ დაკვირვების ფანჯარას. გამოტოვებული, არასწორად ფორმატირებული, დუბლირებული ან ზედმეტად დიდი მთვლელები, არასაკმარისი აქტივობა და მხარდაუჭერელი ნაკადების რეჟიმები ქმნის გაფრთხილებებს ჯანსაღი შეფასების ან გამართვის რეკომენდაციის ნაცვლად. გაფრთხილებებმა შეიძლება იმოქმედოს Nagios-ის სტატუსსა და დაგეგმილ შეტყობინებებზე, როდესაც ჩართულია **შეტყობინება გაფრთხილებებზე**.

წაიკითხეთ გაზომილი მთვლელები და რეკომენდაცია ერთად. კუმულაციური მნიშვნელობები არ ადგენს მიმდინარე დატვირთვას; მთვლელებს შეიძლება ჰქონდეთ განულების განსხვავებული ისტორია და ისინი არ წარმოადგენს ატომურ ანაბეჭდს. პიკური კავშირები შესაძლოა ძველ ლიმიტს ასახავდეს. ნელი მოთხოვნების რაოდენობა დამოკიდებულია `long_query_time`-ზე, ხოლო MySQL-ის დისკის დროებითი ცხრილების მთვლელი შესაძლოა ტოვებდეს მეხსიერებაში ასახულ ფაილებს. დაბალი თანაფარდობა არ ამტკიცებს ვიწრო ადგილის არარსებობას. ბუფერების ან კავშირის ლიმიტების შეცვლამდე დაადასტურეთ ტენდენციები ტიპური დატვირთვის პირობებში, გადახედეთ მოთხოვნის გეგმებსა და კავშირების ხელახალ გამოყენებას და გაზომეთ მეხსიერება **მონაცემთა ბაზის ჰოსტზე**.

თუ მეტრიკები მიუწვდომელია, შეამოწმეთ სერვერის მხარდაჭერა და Cacti-ის ანგარიშის წვდომა `SHOW GLOBAL STATUS` და `SHOW GLOBAL VARIABLES` ბრძანებებზე; Doctor არ ითხოვს გაზრდილ უფლებებს. მთვლელების განმარტებები აღებულია [MySQL სტატუსის ცვლადების ცნობარიდან](https://dev.mysql.com/doc/refman/8.0/en/server-status-variables.html) და [MariaDB სტატუსის ცვლადების ცნობარიდან](https://mariadb.com/docs/server/server-management/variables-and-modes/server-status-variables). MySQLTuner-ის არცერთი სკრიპტი ან კოდი არ გამოიყენება.

სქემის ან კონფიგურაციის მიგრაცია საჭირო არ არის. განათავსეთ პლაგინის ფაილები ჩვეულებრივად; მათი დაბრუნება წაშლის დამატებულ დიაგნოსტიკას. არსებული დაგეგმილი მდგომარეობა შემდეგ გაშვებაზე განახლდება.

## უსაფრთხოების პრინციპები

დიაგნოსტიკური ხელსაწყო მუშაობს პოლერის ან ვებ-სერვერის პრივილეგიებით და კითხულობს გზებს პარამეტრების ცხრილიდან, ამიტომ ფრთხილად უნდა აკონტროლოს, რას უშვებს და რას ცვლის.

- დიაგნოსტიკა მხოლოდ წაკითხვის რეჟიმში მუშაობს. ის არასდროს ცვლის ფაილებს, პარამეტრებს ან მონაცემებს.
- Doctor უშვებს კონფიგურირებულ ბინარულ ფაილს მხოლოდ მაშინ, როდესაც მისი ფაილის სახელი შეესაბამება მოსალოდნელ პროგრამას (`php`, `rrdtool`, `snmpget` ან `snmpwalk`). წინააღმდეგ შემთხვევაში ნებისმიერ პირს, ვისაც პარამეტრების ცხრილში ჩაწერის უფლება აქვს, შეეძლო აერჩია, რას გაუშვებდა Doctor. ნებისმიერი სხვა სახელი ფიქსირდება გაფრთხილებად და არ ეშვება.
- Doctor არასდროს უშვებს კონფიგურირებულ ბინარულ ფაილებს root-ის სახელით და იტყობინება, როდესაც თავად მუშაობს root-ის სახელით.
- შეკეთებები მოდის ფიქსირებული დაშვებულთა სიიდან. თითოეული საჭიროებს ავთენტიფიცირებული ადმინისტრატორის მოქმედებას ვებ-ინტერფეისში ან `--yes` პარამეტრს CLI-ში და თითოეული იწერება Cacti-ის ჟურნალში.

## ენები

Doctor მოიცავს 48 არაინგლისურ თარგმანის კატალოგს `locales/po/` და `locales/LC_MESSAGES/` დირექტორიებში, რომლებიც ფარავს Broad Tier 1 (`ar-SA`, `de-DE`, `es-ES`, `es-419`, `fr-FR`, `hi-IN`, `id-ID`, `it-IT`, `ja-JP`, `ko-KR`, `nl-NL`, `pl-PL`, `pt-BR`, `ru-RU`, `sv-SE`, `tr-TR`, `uk-UA`, `vi-VN`, `zh-CN`, `zh-TW`), აფრიკულ (`af-ZA`, `am-ET`, `ar-EG`, `ar-MA`, `fr-MA`, `fr-SN`, `ha-NG`, `ig-NG`, `mg-MG`, `rw-RW`, `so-SO`, `sw-KE`, `xh-ZA`, `yo-NG`, `zu-ZA`), აზიურ (`bn-BD`, `fa-IR`, `he-IL`, `mr-IN`, `ms-MY`, `ta-IN`, `te-IN`, `th-TH`, `ur-PK`, `fil-PH`) და სამხრეთ-აღმოსავლეთ ევროპულ (`bs-BA`, `hr-HR`, `sr-RS`) ლოკალებს. Cacti აჩვენებს კატალოგს მას შემდეგ, რაც ჩართულია ენის მხარდაჭერა (**კონფიგურაცია > პარამეტრები > ზოგადი > ენის მხარდაჭერა**) და მომხმარებელი ირჩევს ლოკალს, რომელიც Cacti-ის ენის ამომრჩევშია; კატალოგები იმ ლოკალებისთვის, რომლებიც ჯერ არ არის Cacti-ის ამომრჩევში, ამოქმედდება მას შემდეგ, რაც Cacti მათ დაამატებს. ვებ-გვერდი, პარამეტრები და ბრძანების სტრიქონის შეტყობინებები მიჰყვება Cacti-ის ენას; თავად ბრძანების სტრიქონის ანგარიში იყენებს Cacti-ის ნაგულისხმევ ენას, რომელიც ინგლისური რჩება, სანამ არ შეცვლით მას.

მანქანურად წასაკითხი გამომავალი არასდროს ითარგმნება: შემოწმების ID-ები, JSON გასაღებები და სტატუსის მნიშვნელობები, `--format=nagios` და `--format=prometheus` გამომავალი, ჟურნალის სტრიქონები და მხარდაჭერის პაკეტის განყოფილებების სათაურები რჩება ინგლისურად, რათა სკრიპტებმა და მონიტორინგმა ყველა ენაზე უწყვეტად იმუშაოს. თითოეული შემოწმების `summary` და `detail` ტექსტი JSON ანგარიშის ერთადერთი ნათარგმნი ნაწილია.

ლათინოამერიკული ესპანურის კატალოგი (`es-419`) ასევე თან ერთვის, მაგრამ არც Cacti 1.2-ს და არც Cacti 1.3-ს არ აქვს ლათინოამერიკული ესპანურის ლოკალი ასარჩევად, ამიტომ ის ამოქმედდება მხოლოდ მაშინ, როდესაც Cacti მას დაამატებს. მანამდე აირჩიეთ ესპანური (`es-ES`).

Cacti პლაგინის კატალოგს ტვირთავს `plugins/doctor/locales/LC_MESSAGES/<locale>.mo` გზიდან `doctor` ტექსტური დომენით, როგორც 1.2.x-ზე, ასევე 1.3-ზე (1.3 პლაგინის დირექტორიას თავისი კონფიგურირებადი პლაგინების გზით პოულობს).

ხელსაწყოების მენიუ ხსნის მომხმარებლისთვის მინიჭებული უმაღლესი Doctor უფლების შესაბამის გვერდს, ჯგუფური უფლებების ჩათვლით. დამთვალიერებლისა და ოპერატორის ახალ უფლებებს ავტომატური მინიჭება არ აქვს. საწყისი უფლების ID მიბმული რჩება `doctor.php`-ზე როგორც ადმინისტრატორი, რაც ინარჩუნებს მომხმარებლებისა და ჯგუფების არსებულ წვდომას.

დამთვალიერებლის მონაცემები მოდის დაგეგმილი შემოწმებებიდან. დამთვალიერებლის წვდომის მინიჭებამდე ჩართეთ დაგეგმვა; გამოტოვებული ან ვადაგადაცილებული დაკვირვებები ჩანს როგორც **უცნობი** და არასდროს როგორც ჯანსაღი. ისტორია ინახავს ბოლო 20 დაგეგმილ აგრეგირებულ რაოდენობას და არ მოიცავს მოწყობილობების სტატუსს. ოპერატორები ახალ დიაგნოსტიკას აშკარად უშვებენ; ჩვეულებრივი გვერდის განახლება აჩვენებს მათი სესიის ბოლო ანგარიშს.

მოწყობილობების დეტალები და ჯამები იყენებს მიმდინარე მომხმარებლის მოწყობილობების უფლებებს. ჟურნალის ფრაგმენტები დამატებით საჭიროებს Cacti-ის Log Administration უფლებას. საიდუმლო მნიშვნელობები ინიღბება ვებ-სესიაში შენახვამდე ან გამოჩენამდე. CLI წვდომა კვლავ რეგულირდება ოპერაციული სისტემის ანგარიშით.

დადასტურებები პერსონალურია და იწერება Cacti-ის ჟურნალში. ისინი ვრცელდება მხოლოდ იმავე მიგნებასა და მტკიცებულებაზე; შეცვლილი მტკიცებულება მოითხოვს ახალ დადასტურებას. ისინი არასდროს ცვლის წარმატებული/გაფრთხილება/შეცდომა სტატუსს, არ თრგუნავს შეტყობინებებს და არ ნიშნავს ჩავარდნილ შემოწმებას ჯანსაღად. ეს განსხვავდება მიღებული გაფრთხილების გამონაკლისებისგან, რომლებიც გავლენას ახდენს შეტყობინებების პოლიტიკაზე დაკვირვებული სტატუსის შეუცვლელად და აღწერილია ქვემოთ.

თითოეული მოქმედება მოითხოვს POST-ს და ვალიდურ CSRF ტოკენს. შეკეთებები აჩვენებს ცალკე დადასტურების გვერდს გაუქმების არაგამგზავნ ბმულთან ერთად და Cacti-ის ჟურნალში აფიქსირებს მოქმედ მომხმარებელსა და შედეგს.

## ბრძანების სტრიქონი

გაუშვით ეს ბრძანებები Cacti-ის ძირეული დირექტორიიდან Cacti-ის პოლერის მომხმარებლით და არა root-ით:

```console
php plugins/doctor/cli/doctor.php
php plugins/doctor/cli/doctor.php --json
php plugins/doctor/cli/doctor.php --repair=runtime_directories --yes
```

ტექსტური გამომავალი თითოეული შემოწმებისთვის ბეჭდავს ერთ სტრიქონს სტატუსით, კატეგორიით, შეჯამებითა და დეტალით. `--json` ბეჭდავს `summary` ობიექტს სტატუსების რაოდენობებით და `checks` მასივს, რომლის ელემენტებიც შეიცავს `id`, `category`, `status`, `summary`, `detail` და — როდესაც დაშვებული შეკეთება მოქმედებს — `repair`/`repairable` ველებს.

| დასრულების კოდი | მნიშვნელობა |
|---|---|
| `0` | არცერთი შემოწმება არ ჩავარდა, ან მოთხოვნილი შეკეთება წარმატებით დასრულდა. გაფრთხილებები დასრულების კოდს არ ცვლის. |
| `1` | სულ მცირე ერთი შემოწმება ჩავარდა, ან მოთხოვნილი შეკეთება ვერ შესრულდა. |
| `2` | გამოყენების შეცდომა: შეკეთება `--yes`-ის გარეშე (`--preview`-ს ის არ სჭირდება), უცნობი შეკეთების ID, უცნობი გამომავალი ფორმატი, `--symptom`-ისა და ფორმატის მხარდაუჭერელი კომბინაცია, ან Cacti ინსტალაციის ვერ პოვნა. |

Cacti ზრდის `memory_limit`-ს ყველა CLI სკრიპტისთვის, ამიტომ PHP-ის სამუშაო გარემოს კონფიგურაციის შემოწმება აზრიანია მხოლოდ ვებ-გვერდზე.

## დაგეგმილი შემოწმებები და შეტყობინებები

განყოფილებაში **კონფიგურაცია > პარამეტრები > Doctor** ჩართეთ **შემოწმებების გაშვება განრიგით** და აირჩიეთ ინტერვალი 15 წუთიდან ერთ დღემდე. პოლერის ყოველი შესაბამისი ციკლის შემდეგ Doctor ყველა შემოწმებას ფონურ პროცესში უშვებს, რათა თავად პოლერის შესრულების დროზე გავლენა არ ჰქონდეს.

თითოეული გაშვება იწერს ყველა შემოწმების დაკვირვებულ სტატუსს. გაფრთხილების აქტიური გამონაკლისები გავლენას ახდენს შეტყობინებების პოლიტიკაზე ამ დაკვირვების შეუცვლელად. როდესაც შემოწმება იწყებს ან წყვეტს შეცდომით დასრულებას, Doctor ცვლილებას წერს Cacti-ის ჟურნალში და — თუ **შეტყობინებების ელფოსტის მისამართები** მითითებულია — აგზავნის წერილს Cacti-ის ფოსტის პარამეტრებით. **შეტყობინება გაფრთხილებებზე** ამატებს გაფრთხილებაში გადასვლისა და გამოსვლის შეტყობინებებს. პირველი გაშვება მხოლოდ საბაზისო მდგომარეობას აფიქსირებს.

დაგეგმილი ანგარიშები ეშვება მთავარ პოლერზე მონაცემთა ბაზის საკონსულტაციო ბლოკირებით და აქვს ორწუთიანი შესრულების ლიმიტი. Doctor აჩვენებს ბოლო დაწყებისა და წარმატებული დასრულების დროს, რათა გამოტოვებული ან მოძველებული შედეგები ჩანდეს. შედეგები აქტუალურად ითვლება ინტერვალის, პლუს ერთი გამოკითხვის ციკლისა და სამი წუთის განმავლობაში. დაუსრულებელი გაშვება მეორდება 5, 10, 20 და მეტი წუთის შემდეგ, ნორმალურ ინტერვალამდე. შეტყობინების წარუმატებელი მიწოდება ინახება სამ განმეორებით მცდელობამდე მზარდი დაყოვნებით; ამის შემდეგ გაასწორეთ Cacti-ის ფოსტის პარამეტრები და პოლერის მომხმარებლით გაუშვით `php plugins/doctor/cli/doctor.php --scheduled --retry-alerts`. ფოსტის სერვერის მიერ მიღება არ ადასტურებს საფოსტო ყუთში ჩაბარებას.

იგივე ჩანართი განსაზღვრავს ზღვრებს პოლერის შესრულების დროისთვის (ინტერვალის 80%), RRA თავისუფალი დისკის სივრცისთვის (გაფრთხილება 10%-ზე დაბლა, შეცდომა 2%-ზე დაბლა), მონაცემთა ბაზის საათის აცდენისთვის (გაფრთხილება 5 წამზე მეტი, შეცდომა 60-ზე მეტი) და Cacti-ის ჟურნალის ზომისთვის (100 MB). ცარიელი ან არავალიდური მნიშვნელობები ბრუნდება ამ ნაგულისხმევ პარამეტრებზე.

## მონიტორინგის ინტეგრაცია

```console
php plugins/doctor/cli/doctor.php --format=nagios
php plugins/doctor/cli/doctor.php --format=prometheus > /var/lib/node_exporter/textfile/cacti_doctor.prom
```

`--format=nagios` ბეჭდავს ერთ სტატუსის სტრიქონს წარმადობის მონაცემებით და სრულდება კოდით `0` (OK), `1` (WARNING) ან `2` (CRITICAL), ამიტომ Nagios, Icinga ან ნებისმიერი თავსებადი სისტემა მას პირდაპირ გაუშვებს. `--format=prometheus` წერს Prometheus-ის ტექსტურ ფორმატს node_exporter-ის textfile კოლექტორისთვის: `cacti_doctor_check_status` თითო შემოწმებაზე (0 წარმატებული ან მიღებული გაფრთხილება, 1 საყურადღებო გაფრთხილება, 2 შეცდომა), `cacti_doctor_check_observed_status` გამონაკლისებამდე, `cacti_doctor_check_accepted`, `cacti_doctor_checks` თითო სტატუსზე და `cacti_doctor_last_run_timestamp_seconds`. JSON შემოწმების სტრიქონები შეიცავს `assessment` ველს; `not_assessed` ნიშნავს, რომ შემოწმებამ ხელმისაწვდომი მონაცემებით დასკვნა ვერ გამოიტანა.

## შეკეთების პოლიტიკა

Doctor მოიცავს ერთ შეკეთებას — `runtime_directories`. ის ქმნის დაკარგულ Cacti-ის სამუშაო დირექტორიებს და ამატებს მფლობელის წაკითხვის, ჩაწერისა და შესრულების უფლებებს არსებული უფლებების მოხსნის გარეშე.

Cacti 1.3-ზე ის მიმართულია `$cache_path`, `$log_path` და `$rra_path` გზებზე, სხვა შემთხვევაში კი ინსტალაციის `cache`, `log` და `rra` დირექტორიებზე. ის ტოვებს უკვე ჩაწერად დირექტორიებს, უარს ამბობს Cacti-ის ინსტალაციის გარეთ მყოფ დირექტორიებზე (მაგალითად, `/var/log`-ში მდებარე ჟურნალის დირექტორიაზე), სიმბოლურ ბმულებზე და root-ის სახელით გაშვებაზე. ის არასდროს მიჰყვება `path_cactilog`-ს, ამიტომ კოდის დირექტორიაში კონფიგურირებული ჟურნალის ფაილი შეკეთებას იქ ვერ გადაამისამართებს. დიაგნოსტიკა ყველა ვერსიაზე კვლავ ამოწმებს კონფიგურირებული ჟურნალის ფაილის დირექტორიას.

ის არ ცვლის მფლობელობას, არ უშვებს shell ბრძანებებს, არ გადაწერს კონფიგურაციას და არ ცვლის Cacti-ის აპლიკაციის მონაცემებს. თითოეული ახალი შეკეთება უნდა შეიცავდეს დიაგნოსტიკას, დაშვებულთა სიის დამმუშავებელს, დადასტურებას, აუდიტის ჟურნალირებასა და ტესტებს.

## სიმპტომების გამოკვლევა

ოპერატორებსა და ადმინისტრატორებს შეუძლიათ Doctor-ის გვერდზე აირჩიონ **სიმპტომის გამოკვლევა**. იგივე წესები ხელმისაწვდომია `--symptom=graphs_stopped`, `slow_polling`, `devices_missing` ან `alerts_missing` პარამეტრებით, ტექსტური ან JSON გამომავალით. მხარდაჭერის პაკეტები მოიცავს შესაბამის სიმპტომების გამოკვლევებს.

თითოეული კანდიდატი ჩამოთვლის დაკვირვებულ შემოწმებებსა და გადამოწმების შემდეგ ნაბიჯს. კანდიდატები ჰიპოთეზებია და არა დადასტურებული პირველმიზეზები. გამოტოვებული, შეუფასებელი ან მოძველებული დაკვირვებები არასდროს ადგენს მიზეზს. ვებ-გამოკვლევები იყენებს უფლებებით გაფილტრულ ანგარიშს; CLI ანგარიშები იყენებს ოპერაციული სისტემის ანგარიშის წვდომას.

## RRD განახლების აქტუალობა

`filesystem.rrd_stale` ამოწმებს 500-მდე აქტიურ მონაცემთა წყაროს, გამორთული და მიუწვდომელი მოწყობილობების გამოკლებით. დიდ ინსტალაციებში შერჩევა ყოველ საათში იცვლება, რათა განმეორებითმა გაშვებებმა სხვადასხვა ფაილი დაფაროს. ის ადარებს ფაილის ცვლილების დროს პოლერის ინტერვალის, წყაროს RRD ბიჯისა და პროფილის ბიჯის უდიდეს მნიშვნელობას, გამრავლებულს **RRD მოძველების ინტერვალებზე** (ნაგულისხმევად 3). ის აჩვენებს სამ უძველეს მოძველებულ ფაილს და დაზარალებული მოწყობილობების რაოდენობას. ვებ-შედეგები მოიცავს მხოლოდ დაშვებულ მოწყობილობებს.

`filesystem.rrd_files` ცალკე არსებობის შემოწმებაა. ის ეძებს RRD ფაილს 5,000-მდე აქტიური მონაცემთა წყაროსთვის, გამორთულ ან მიუწვდომელ მოწყობილობებზე მყოფთა ჩათვლით, და იყენებს იმავე საათობრივ შერჩევას.

Boost დისკზე ჩაწერის დაშვებად ამატებს თავისი კონფიგურირებული ჩაწერის ინტერვალის ორმაგ მნიშვნელობას. სხვა გადავადებული ჩამწერისთვის დააკონფიგურირეთ **გადავადებული RRD ჩაწერის დაშვება (წამი)**. გამოცხადებული `RRDCACHED_ADDRESS` დაშვების გარეშე, ან არავალიდური Boost ინტერვალი, იძლევა შეუფასებელ შედეგს. Doctor არასდროს აცარიელებს ქეშს ამ შემოწმების შესასრულებლად. ცვლილების დრო დისკის აქტივობის ნიშანია და არა მონაცემთა წარმატებული შეგროვების მტკიცებულება. გარე ქეშირება, რომელსაც Doctor ვერ ამჩნევს, აშკარად უნდა დაკონფიგურირდეს.

დაკარგული, წაუკითხავი და მომავლის თარიღიანი ფაილები ითვლება დეტალებში. შედეგი შეუფასებელია მხოლოდ მაშინ, როდესაც შერჩეული არცერთი ფაილი არ არის წაკითხვადი. შერჩეული შედეგი მიუთითებს, რომ ის ფარავს ინსტალაციის მხოლოდ ნაწილს; წარმატებული შემოწმება არ ფარავს შეუმოწმებელ ფაილებს.

## შეკეთების წინასწარი ხედვა და აუდიტის ისტორია

ადმინისტრატორის შეკეთების გვერდი აჩვენებს თითოეულ დაზარალებულ გზას, შემოთავაზებულ მოქმედებას, მიმდინარე უფლებებსა და სამიზნე უფლებებს. დამტკიცება მიბმულია ამ წინასწარ ხედვაზე, მოქმედ მომხმარებელსა და ხუთწუთიან ვადაზე. დადასტურება ამოწურავს წინასწარ ხედვას; ფაილური სისტემის ცვლილება მოითხოვს ახალ წინასწარ ხედვას. root-ით გაშვება, ინსტალაციის გარეთ არსებული გზები, შეკეთების საჭიროების მქონე ბმულები და დაუკმაყოფილებელი ფაილური სისტემის უფლებები ბლოკავს დამტკიცებას.

`--repair=runtime_directories --preview` ბეჭდავს მხოლოდ წაკითხვის JSON გეგმას. `--repair=runtime_directories --yes` ამტკიცებს ახლად გამოთვლილ CLI გეგმას და გაშვებამდე ხელახლა ამოწმებს მას. CLI ანგარიშს უკვე უნდა ჰქონდეს ინსტალაციის შეკეთების უფლება; ის ვებ-როლებს არ მემკვიდრეობს.

ფაილურ სისტემაში ნებისმიერ ცვლილებამდე უნდა შეინახოს სტრუქტურირებული `repair.started` ჩანაწერი. დაკავშირებული `repair.completed` ჩანაწერი შეიცავს შეკეთების შემდგომ ანაბეჭდსა და გადამოწმების შედეგს. შეწყვეტილი ოპერაცია გამოკვლევისთვის ტოვებს დაწყების ჩანაწერს. დასრულების აუდიტის შეცდომა შეცდომად ფიქსირდება მაშინაც კი, თუ ფაილურ სისტემაში ცვლილებები განხორციელდა. Doctor ამატებს მფლობელის უფლებებს და ქმნის დირექტორიებს; ის არ ცდილობს ავტომატურ უკან დაბრუნებას.

ადმინისტრატორებს, რომლებსაც აქვთ Cacti-ის Settings/System Utilities უფლება, შეუძლიათ Doctor-ის გვერდზე ნახონ ბოლო 20 აუდიტის ჩანაწერი. პლაგინი ინახავს ბოლო 200 ჩანაწერს `plugin_doctor_audit` ცხრილში; Cacti-ის ჟურნალი ასევე იწერს მათ ID-ებს, მოქმედებებსა და შემსრულებლებს. აუდიტის მონაცემები დაფარულია.

## მიღებული გაფრთხილებები

ადმინისტრატორებს, რომლებსაც აქვთ Cacti-ის Settings/System Utilities უფლება, შეუძლიათ Doctor-ის გვერდზე ახალი, შეფასებული გაფრთხილებიდან შექმნან **გაფრთხილების გამონაკლისი**. გამონაკლისი საჭიროებს პასუხისმგებელ პირს, მიზეზს და გადახედვის UTC თარიღს 90 დღის ფარგლებში. მისი ვადა იწურება ამ თარიღის დასაწყისში შუაღამით UTC. შესაძლებელია 100-მდე გამონაკლისის კონფიგურაცია. სია აჩვენებს ვადაგასულ ჩანაწერებს და იმ ID-ებს, რომლებიც მიმდინარე ანგარიშში არ არის, და იძლევა წაშლის საშუალებას.

დაკვირვებული გაფრთხილება კვლავ ჩანს, პასუხისმგებელ პირთან, მიზეზთან და ვადასთან ერთად დიაგნოსტიკის დეტალებში. JSON ინარჩუნებს დაკვირვებულ სტატუსს და ამატებს `accepted` და `acceptance` მეტამონაცემებს. Nagios გამორიცხავს აქტიურ მიღებულ გაფრთხილებებს დასრულების სიმძიმიდან, მაგრამ მათ სახელებს აჩვენებს გამომავალში. Prometheus ექსპორტს უკეთებს როგორც დაკვირვებულ, ასევე საყურადღებო სიმძიმეს. ჩვეულებრივი CLI დასრულების კოდი უცვლელია: გაფრთხილებები ისედაც აბრუნებს ნულს, ხოლო შეცდომები — ერთს.

გამონაკლისის მოქმედებისას დაგეგმილი გაფრთხილების შეტყობინებები ითრგუნება; ვადის გასვლა ან წაშლა კვლავ არსებულ გაფრთხილებას ხელახლა ხდის შეტყობინების საგნად. შეცდომაზე გადასვლა და შეცდომიდან აღდგენა კვლავ იწვევს შეტყობინებებს. შეუფასებელი შედეგი ან შეცდომა ვერ მიიღება გამონაკლისად. პერსონალური დადასტურება ცალკეა და არაფერს თრგუნავს. გამონაკლისის შექმნა და წაშლა ტრანზაქციულად სრულდება აუდიტის ჩანაწერთან ერთად.

განახლება ქმნის `plugin_doctor_audit` და `plugin_doctor_acceptance` ცხრილებს Cacti-ის აპლიკაციის მონაცემების შეუცვლელად. წაშლამდე გააკეთეთ საჭირო ისტორიის ექსპორტი: დეინსტალაცია შლის პლაგინის ორივე ცხრილსა და მის პარამეტრებს. პლაგინის ფაილების ძველ ვერსიაზე დაბრუნება ტოვებს ცხრილებს გამოკვლევისთვის, მაგრამ ძველი ვერსიები გაფრთხილების გამონაკლისებს არ ითვალისწინებს.

## პლაგინების შემოწმებები (`doctor_register_checks`)

ჩართულ Cacti-ის პლაგინებს შეუძლიათ დაამატონ მხოლოდ წაკითხვის დიაგნოსტიკური შემოწმებები და არასავალდებულო მხარდაჭერის პაკეტის დანართები `doctor_register_checks` ჰუკის რეგისტრაციით:

```php
api_plugin_register_hook('sample', 'doctor_register_checks', 'sample_doctor_checks', 'setup.php');
```

Doctor იძახებს ჩართულ, არაინტეგრირებულ პლაგინებს, რომლებიც რეგისტრირებულია `doctor_register_checks`-ზე (`doctor` და `cacti` გამოტოვებულია), და ჰუკის ფაილს მკაცრად პლაგინის საკუთარ დირექტორიაში პოულობს. უკუგამოძახება იღებს `['mode' => 'run' | 'list', 'plugin' => '<slug>']` და აბრუნებს ან შემოწმების დესკრიპტორების სიას, ან ობიექტს `checks` და არასავალდებულო `attachments` ველებით:

```php
function sample_doctor_checks($context) {
	return [
		'checks' => [
			[
				'id'          => 'sample.queue_depth',
				'plugin'      => 'sample',
				'category'    => 'Sample',
				'title'       => 'Sample queue depth',
				'status'      => 'ok',
				'message'     => 'Queue is healthy.',
				'details'     => ['pending' => 0],
				'remediation' => ''
			]
		],
		'attachments' => [
			[
				'title'   => 'Sample diagnostics',
				'content' => "worker=ok\n"
			]
		]
	];
}
```

თითოეული პლაგინის შემოწმების დესკრიპტორი ჩართვამდე გადის ვალიდაციას:

- სავალდებულო გასაღებები: `id`, `plugin`, `category`, `title`, `status`, `message`, `details` და `remediation`.
- `plugin` უნდა ემთხვეოდეს რეგისტრირებულ პლაგინის სლაგს (`[a-z0-9_]{1,64}`). `id` უნდა აკმაყოფილებდეს `[a-z0-9_.]{1,128}` შაბლონს, იწყებოდეს `<plugin>.`-ით და არ ეჯახებოდეს არსებულ ძირითად ან პლაგინის შემოწმების ID-ს.
- `status` უნდა იყოს `ok`, `warn`, `fail` ან `info`. Doctor-ის ანგარიშებში `ok` აისახება როგორც `pass`; `info` საინფორმაციოა და არ იწვევს შეცდომებს CLI-ში, Nagios-ში, Prometheus-ში ან დაგეგმილ შეტყობინებებში.
- `category` (64 ბაიტამდე) და `title` (256 ბაიტამდე) უნდა იყოს არაცარიელი სტრიქონები მართვის სიმბოლოების გარეშე. `message` (არაცარიელი, 2048 ბაიტამდე) და `remediation` (2048 ბაიტამდე) უნდა იყოს სტრიქონები.
- `details` იღებს სტრიქონს (8192 ბაიტამდე) ან სკალარულ/ჩადგმულ მასივს (მაქსიმალური სიღრმე 4, JSON-კოდირებული 16384 ბაიტამდე; ობიექტები და რესურსები უარყოფილია).
- არასავალდებულო მხარდაჭერის პაკეტის დანართები საჭიროებს არაცარიელ `title`-ს (128 ბაიტამდე, მართვის სიმბოლოების გარეშე) და `content` სტრიქონს 65536 ბაიტამდე (64 KiB).

Doctor ზღუდავს რაოდენობას 32 შემოწმებამდე და 8 დანართამდე თითო პლაგინზე (სულ 64 პლაგინის შემოწმება და 32 დანართი). თითოეული ჰუკი ეშვება საკუთარ `try`/`catch` საზღვარში, რათა გამონაკლისები ან არამასიური მონაცემები დაიფაროს და ჩაიწეროს Cacti-ის ჟურნალში (`DOCTOR` განყოფილება) ძირითადი შემოწმებებისა და სხვა პლაგინების დაზიანების გარეშე. არასწორი დესკრიპტორები უარყოფილია და იწერება ჟურნალში, ხოლო იმავე პლაგინის ვალიდური დესკრიპტორები კვლავ ეშვება. პლაგინის შემოწმებები ყოველთვის მხოლოდ წაკითხვისაა (`repairable: false`), ხოლო სტრიქონული მნიშვნელობები და სენსიტიური ასოციაციური გასაღებები იფარება ჩვენებამდე, ექსპორტამდე ან პაკეტირებამდე. ვალიდირებული პლაგინის შემოწმებები ჩანს ვებ-ინტერფეისში, CLI ტექსტურ/JSON/Nagios/Prometheus გამომავალში, დაგეგმილ სტატუსის თვალთვალსა და მხარდაჭერის პაკეტებში.

### თარგმანები

მომხმარებლისთვის ხილული ყველა შეტყობინება მოაქციეთ `__('...', 'doctor')`-ში (ან `__n()`, `__x()`, `__esc()`), ხოლო მნიშვნელობის შემცველი წინადადებისთვის გამოიყენეთ ერთი ფორმატის სტრიქონი თანმიმდევრული `%s`/`%d` ჩამნაცვლებლებით ნაწილების მიერთების ნაცვლად. Cacti-ის `__()` ფუნქცია შეტყობინებას აფორმატებს მხოლოდ მაშინ, როდესაც ის ფორმატის სპეციფიკატორს შეიცავს და არ უჭერს მხარს პოზიციურ `%1$s` ფორმებს. ის ასევე ფორმატირებამდე გარდაქმნის `%%`-ს `%`-ად, ამიტომ არასდროს ჩასვათ პროცენტის ლიტერალური ნიშანი შეტყობინებაში: გადაეცით მნიშვნელობა თავისი ნიშნით არგუმენტად (`__('Usage: %s', '50%', 'doctor')`). ჟურნალის სტრიქონები რჩება ინგლისურად: შეკეთების ტექსტისთვის გამოიყენეთ `doctor_repair_message()`, ხოლო იმ შეტყობინებებისთვის, რომლებიც იწერება ჟურნალში და ითარგმნება მხოლოდ ჩვენებისას — `doctor_n_()`. შემოწმების ID-ები, JSON გასაღებები, სტატუსის საკვანძო სიტყვები, მონიტორინგის გამომავალი და ჟურნალის სტრიქონები დატოვეთ უთარგმნელი.

`locales/build_gettext.sh` ხელახლა აგენერირებს შაბლონს `locales/po/cacti.pot`, აერთიანებს მას თითოეულ კატალოგთან `locales/po/<locale>.po` და აკომპილირებს `locales/LC_MESSAGES/<locale>.mo`-ს; დააკომიტეთ სამივე. CI უშვებს `sh locales/build_gettext.sh --check`-ს, რომელიც შეცდომით სრულდება მოძველებულ შაბლონზე, კატალოგში გამოტოვებულ ან fuzzy ჩანაწერზე, განსხვავებულ ჩამნაცვლებელზე ან მოძველებულ კომპილირებულ ფაილზე. შესაბამისად, შეცვლილი შეტყობინების თარგმანები იმავე pull request-ში უნდა განახლდეს. ამისთვის საჭიროა GNU gettext (`xgettext`, `msgmerge`, `msgfmt`, `msgunfmt`). ახალი ენა წარმოადგენს ახალ `<locale>.po` ფაილს Cacti-ის ლოკალების სახელდებით (მაგალითად `pt-BR`).
